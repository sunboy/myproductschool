{"hook_text": "Claude Code's context window is finite, and everything it reads, runs, and says lives there until the session ends. A bloated window produces worse answers, not just slower ones. Keeping it lean is the single discipline that separates a sharp session from a confused one.", "body_mdx": "## What Lives in the Context Window\n\nA Claude Code session has one shared context window. Every turn, the full window is sent to the model so it can decide what to do next. Four things fill it up, and they accumulate:\n\n- **The conversation.** Your messages and Claude's replies, every turn, in order.\n- **File contents.** Every file Claude reads stays in the window. A 1,200-line component read in turn 3 is still there in turn 30.\n- **Tool outputs.** The result of every `Bash` command, every `Grep`, every search. A `npm run build` that dumps 400 lines of warnings puts all 400 lines into the window.\n- **System instructions.** The base prompt plus your `CLAUDE.md` and any loaded skills.\n\nNothing leaves on its own. The window only grows over a session until it hits the limit or the session ends.\n\n```mermaid\ngraph TD\n  subgraph Window[Context Window: fills over the session]\n    S[System prompt and CLAUDE.md]\n    C[Conversation history]\n    F[Files read: stay resident]\n    T[Tool outputs: stay resident]\n  end\n  S --> Limit[Token limit]\n  C --> Limit\n  F --> Limit\n  T --> Limit\n  Limit -->|exceeded| Compact[Compaction: summarize and drop detail]\n```\n\n## Why a Bloated Context Degrades Quality\n\nThe instinct is that more context means more to work with, so the answer should be better. The opposite is true past a point.\n\nWhen the window is full of material that does not bear on the current task, the model has to find the relevant signal inside a large pile of noise. Important details get diluted. The model is more likely to fixate on something it read twenty turns ago that is no longer true, or to lose track of a recent instruction because it is buried under a wall of build output. Attention is finite, and spreading it across irrelevant tokens costs accuracy.\n\nThe practical symptoms are familiar. The model starts repeating work it already did. It reintroduces a bug you fixed three turns back. It answers a question you did not ask because the phrasing matched something earlier in the session. These are signs the window has too much in it, not signs the model got worse.\n\nA lean window keeps the relevant facts dense and recent, which is the state the model performs best in.\n\n## Compaction and Summarization\n\nWhen a session approaches the token limit, Claude Code compacts. It summarizes the earlier part of the conversation into a condensed form and drops the verbatim detail. This keeps the session alive past the raw limit, but it is a lossy operation. The summary keeps the gist and discards specifics, so a file you read in full early on becomes a one-line note that it was read.\n\nCompaction is a safety net, not a strategy. After a compaction, the model is working from a summary of its own earlier reasoning, and fine detail is gone. If a precise fact from early in the session matters later, it may no longer be available at full fidelity. The better move is to manage the window so compaction rarely fires, rather than relying on it to rescue a session that grew without discipline.\n\n## The Discipline: Read Only What You Need\n\nThe largest source of avoidable bloat is reading more than the task requires. Three habits keep it under control.\n\n**Read targeted, not whole.** When you know the function you need is near line 400 of a 2,000-line file, read that range, not the entire file. Reading the whole file when you need forty lines spends the other 1,960 lines of budget on nothing.\n\n**Search before you read.** Use `Grep` to find where something lives, then read only the file and the region the search points to. Searching narrows the read; reading without searching first usually means reading too much.\n\n**Do not re-read.** A file already in the window does not need to be read again. If you edited it, the edit is reflected; re-reading just duplicates content that is already resident.\n\n## Isolate Big Searches in Subagents\n\nSome work is inherently noisy. Searching a large codebase to answer a question, reading two dozen files to understand a subsystem, or scanning a long log all produce far more output than the final answer needs. Doing that in the main session dumps every intermediate file and search result into the window, and it stays there for the rest of the session.\n\nA subagent runs in its own separate context window. The orchestrator sends it a question, the subagent reads whatever it needs, and it returns only a summary. The intermediate reads never touch the main window. The orchestrator pays the cost of the answer, not the cost of the investigation.\n\n```mermaid\ngraph LR\n  M[Main session: stays lean] -->|find where rate limiting is enforced| A[Subagent]\n  A -->|reads 18 files internally| A\n  A -->|returns: 3 lines naming the files and the function| M\n```\n\nThe asymmetry is the whole point. The subagent might read eighteen files to answer the question, but only its three-line conclusion enters the main session. The eighteen files are isolated in the subagent's window, which is discarded when it returns. The main thread stays clean and keeps room for the actual work.\n\n## A Concrete Example\n\nSuppose the task is: find why a checkout endpoint returns a 500 under load and fix it.\n\nThe context-heavy approach reads the route handler, then the payment library, then the database client, then the connection pool config, then the middleware, then three related test files, all into the main window, while running the failing test twice and pasting both full outputs. By the time the fix is ready, the window holds seven large files and two long test dumps. The model is now reasoning about the one-line fix while carrying all of that resident, and it starts second-guessing a change it already validated because an earlier file in the window suggested a different pattern.\n\nThe lean approach does this instead. It spawns a subagent with the brief: \"Find why `/api/checkout` returns 500 under load. Read what you need. Return the root cause, the file and line, and nothing else.\" The subagent reads the seven files in its own window and returns: \"The connection pool in `src/lib/db/pool.ts` is capped at 5. Under load, requests past 5 wait past the 2s timeout and the handler throws. Raise the cap or add queuing.\" The main session now holds three lines instead of seven files. It opens `pool.ts`, reads the relevant fifteen lines, makes the change, and runs the test once. The window stayed small, the model never lost the thread, and the fix landed without the model arguing with stale context.\n\nSame outcome. One session ends bloated and shaky; the other ends lean and certain.\n\n## When to Start a Fresh Session\n\nContext does not need to live forever. When the current task is done and the next task is unrelated, a fresh session is the cleanest reset available. Starting over discards everything irrelevant and gives the next task a window that holds only what it needs.\n\nStart fresh when the topic changes substantially, when a compaction has already fired and detail you care about is gone, or when the session feels like it is dragging old decisions into new work. A long session is not a badge of efficiency. Carrying an hour of unrelated history into a new task is the same bloat problem in a different shape.\n\nThe exception is when continuity genuinely matters, for example a multi-step refactor where every step depends on decisions made earlier. There, keep the session and lean on tight reads to control the budget. The rule is simple: keep the session when the history is load-bearing, drop it when it is dead weight.\n\n## Planning Up Front Reduces Wasted Context\n\nThe cheapest context is the context you never spend. A few minutes of planning before any file is read pays for itself in window budget.\n\nWhen the plan is clear, reads are targeted. You know which files matter and which regions of them, so you read those and skip the rest. Without a plan, the session explores, and exploration reads broadly and speculatively, pulling in files that turn out to be irrelevant but stay in the window anyway. Planning converts a wide, expensive search into a narrow, cheap set of reads.\n\nThe planning also tells you what to delegate. If the plan has a step that requires understanding a large subsystem, that is the step to hand to a subagent rather than investigate inline. Deciding that before you start keeps the noisy work out of the main thread from the beginning, instead of cleaning up a bloated window after the fact.\n\nLean context is not about doing less. It is about keeping the window dense with what matters so the model's attention lands where the work is. Read narrow, isolate the noise, reset when the history goes stale, and plan before you spend. The output quality follows the discipline."}
