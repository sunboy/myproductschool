{"hook_text": "A skill extends one machine. A plugin extends a team. Plugins bundle skills, slash commands, agents, hooks, and MCP servers into one installable unit that anyone can add with a single command.", "body_mdx": "## The Limit of Loose Files\n\nSlash commands and skills are powerful, but they live as loose files in `.claude/`. That works for one person on one machine. The moment you want a teammate to have the same setup, the model breaks down. You end up copying directories, pasting setup instructions into a wiki, and watching everyone's configuration drift apart over the following weeks.\n\nA plugin fixes the distribution problem. It packages a set of extensions into one named unit with a version number, and that unit installs with a single command. When you ship a plugin, everyone who installs it gets the exact same commands, skills, agents, hooks, and tool servers, configured the same way. Updates flow through the same channel. The setup stops being tribal knowledge.\n\n## What a Plugin Can Contribute\n\nA plugin is not a new kind of capability. It is a container for the capabilities Claude Code already has. One plugin can bundle any combination of five things:\n\n- **Slash commands** that drop into the session as `/command-name`\n- **Skills** with their full directory of supporting files\n- **Subagents** that handle delegated tasks with their own context and tools\n- **Hooks** that fire on events like file edits, tool calls, or session start\n- **MCP servers** that connect Claude Code to external systems such as a database, an issue tracker, or an internal API\n\nThe value is the combination. A review skill is useful on its own. A review skill plus a slash command that invokes it, plus a hook that runs it automatically before every commit, plus an MCP server that reads your CI results: that is a complete workflow, shipped as one thing.\n\n## The Structure of a Plugin\n\nEvery plugin is a directory with a manifest at its root and a set of conventional subdirectories. The manifest, `plugin.json`, names the plugin and declares what it contains. The subdirectories hold each kind of contribution.\n\n```\nmy-team-plugin/\n  .claude-plugin/\n    plugin.json          ← manifest: name, version, description\n  commands/\n    review.md            ← becomes /review\n    release.md           ← becomes /release\n  skills/\n    db-migration/\n      SKILL.md\n      examples/\n        add-column.sql\n  agents/\n    test-writer.md       ← a subagent definition\n  hooks/\n    hooks.json           ← event-to-action bindings\n  .mcp.json              ← MCP server definitions\n```\n\nThe manifest itself is small. It carries the identity of the plugin and points at anything that lives outside the default locations.\n\n```json\n{\n  \"name\": \"my-team-plugin\",\n  \"version\": \"1.2.0\",\n  \"description\": \"Review, release, and migration workflows for the platform team\",\n  \"author\": { \"name\": \"Platform Team\" }\n}\n```\n\nWhen the plugin is installed, Claude Code reads the manifest, then discovers the commands, skills, agents, hooks, and MCP servers from their conventional directories. The author writes the same files as before. The plugin format is the wrapper that makes those files portable.\n\n## Marketplaces\n\nA plugin needs a place to live so others can find and install it. That place is a marketplace. A marketplace is a git repository (or a hosted catalog) with a manifest listing the plugins it offers. It can hold one plugin or many.\n\nAdding a marketplace registers its catalog. Installing a plugin pulls it from a registered marketplace and activates its contributions for your sessions.\n\n```bash\n# Register a marketplace from a git repo\n/plugin marketplace add your-org/claude-plugins\n\n# Install a plugin from it\n/plugin install my-team-plugin@your-org\n```\n\nThe marketplace is what turns a plugin from a folder on your laptop into something a hundred engineers can install the same afternoon. A team publishes one repo, every engineer registers it once, and from then on new plugins and new versions arrive through the same path.\n\n```mermaid\ngraph TD\n  A[Marketplace repo] -->|lists| B[plugin.json manifest]\n  B --> C[commands/]\n  B --> D[skills/]\n  B --> E[agents/]\n  B --> F[hooks/]\n  B --> G[.mcp.json]\n  H[Engineer runs /plugin install] -->|pulls from| A\n  H --> I[All five contributions active in session]\n```\n\n## When to Reach for a Plugin\n\nThe decision between a one-off skill and a plugin comes down to one question: who needs this, and how does it reach them?\n\nReach for a loose skill or command when the workflow is yours alone, still changing shape, and lives in one repository. Writing a `plugin.json` for a command only you use adds ceremony with no payoff. Keep it in `.claude/commands/` and iterate.\n\nReach for a plugin when any of these are true. The workflow needs to reach more than one person, so distribution matters. It combines several pieces (a command, a hook, and an MCP server that only make sense together), so bundling matters. It needs a version, because you will change it and people need to know which version they are running. Or it crosses repositories, because the same review protocol should apply everywhere your team works, not just in one project.\n\nA useful rule: the first time you find yourself explaining your `.claude/` setup to a colleague so they can copy it, you have outgrown loose files. Package it.\n\n## How Plugins Compose With the Harness\n\nA plugin's contributions do not live in a separate sandbox. They merge into the same session as everything else. A command from a plugin sits beside your project's local commands in the `/` menu. A skill from a plugin is discoverable exactly like a skill you wrote by hand. A hook from a plugin fires on the same events as a hook in your local settings.\n\nThis composition is the point, and it carries one consequence worth holding in mind. Because plugin contributions merge with your own, naming and scope matter. Two plugins that both define a `/deploy` command, or two hooks that both fire on the same pre-commit event, will both be active. Plugins are most predictable when each one owns a clear slice of the workflow and names its commands distinctly. A plugin named for its domain, with commands prefixed or scoped to that domain, stays legible even when a session has five plugins loaded at once.\n\n## A Worked Example\n\nConsider a backend team that has settled on a way of working. Every database change goes through a migration written to a strict format. Every pull request gets reviewed against the same checklist. The team's issue tracker holds the context for why each change exists. Today this knowledge is spread across a wiki page, a few `.claude/commands/` files on the lead engineer's machine, and a lot of repeated explanation.\n\nPackaged as a plugin, it becomes one install. The `commands/migration.md` file encodes the migration format and runs the checks. The `skills/db-review/` directory holds the review rubric with example diffs to score against. A pre-commit hook in `hooks/hooks.json` runs the review automatically so nobody forgets. And an MCP server defined in `.mcp.json` connects to the issue tracker, so Claude Code can read the ticket behind a branch without anyone pasting it in.\n\n```bash\n# A new engineer joins the team\n/plugin marketplace add backend-team/claude-plugins\n/plugin install db-workflow@backend-team\n```\n\nTwo lines, and the new engineer has the team's entire database discipline. The migration format, the review standard, the automatic pre-commit check, the issue-tracker connection. None of it was explained, and none of it can drift, because everyone is running the same version of the same plugin. When the team tightens the review rubric next month, they bump the version and publish. The update reaches everyone through the channel they already registered.\n\nThe mental model is layered. Your global `~/.claude/` configuration is the base. Your project's `.claude/` directory adds to it. Installed plugins add another layer on top. Claude Code reads all of them and presents one combined set of capabilities. The plugin format does not change what a skill or a hook is. It changes how a coherent set of them travels from one engineer to the whole team, with a version attached and a single command to install.\n\nThat is the whole idea. You already know how to write a skill, a command, a hook, and an MCP server. A plugin is the unit that lets you hand all of them to someone else at once, and update them later without asking anyone to copy a folder again."}
