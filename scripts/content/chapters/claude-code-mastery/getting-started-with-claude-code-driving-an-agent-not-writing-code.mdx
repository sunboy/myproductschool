The skill is learning to drive it.", "body_mdx": "## What Claude Code Actually Is\n\nMost coding tools complete the line you are typing. Claude Code does something different. It is an agentic CLI tool, which means it takes a goal and works toward it across multiple steps, using the same tools a human engineer would use at the terminal. It reads files. It edits them. It runs build commands, tests, and git operations. Then it reports what it did and waits for your next instruction.\n\nThe shift in mental model is the whole game. Autocomplete predicts the next token in the file you are looking at. An agent decides which files to open, what to change, and how to verify the change worked. The difference is the difference between a fancy keyboard and a junior engineer who happens to be very fast and never gets tired.\n\nThis is why \"prompt engineering\" is the wrong frame. The real skill is closer to delegation. You state intent clearly, you give the agent the context it needs, and you review what comes back. The better your intent and your review, the better the output.\n\n## How a Session Works\n\nA Claude Code session runs in your terminal, inside a project directory. When it starts, it reads any CLAUDE.md files in the directory tree and loads them as standing context. From there, the loop is simple to describe and worth internalizing.\n\nYou type an instruction. Claude Code decides what it needs to know, reads the relevant files, makes a plan, and starts acting. Acting means calling tools: opening a file, editing it, running a command. After each action it sees the result, which informs the next action. When it has done enough to address your instruction, it stops and tells you what happened. Then control returns to you.\n\n```mermaid\ngraph TD\n  A[You state intent] --> B[Claude reads relevant files]\n  B --> C[Claude plans the change]\n  C --> D[Claude edits files / runs commands]\n  D --> E[Claude observes the result]\n  E --> F{Goal met?}\n  F -->|No| C\n  F -->|Yes| G[Claude reports back]\n  G --> H[You review]\n  H --> A\n```\n\nThe part people miss is the inner loop between planning and observing. Claude Code does not edit blindly. It runs a command, reads the output, and adjusts. When a test fails, it sees the failure and tries a fix. This is what makes it an agent rather than a code generator: it responds to the actual state of your project, not just to your words.\n\n## The REPL Loop You Are Now Part Of\n\nThink of the whole session as a read-eval-print loop where you and the agent take turns. You read the current state of the code and decide what should change next. You state that as an instruction. The agent evaluates it by doing work. It prints a result. You read again. The unit of progress is one of these turns, not one keystroke.\n\nThis changes how you work. Instead of writing every line, you describe an outcome and then judge whether the agent reached it. A good turn is a clear, bounded instruction: \"Add input validation to the signup route and run the tests.\" A bad turn is vague or unbounded: \"Make the auth better.\" The first gives the agent a goal it can verify. The second forces it to guess what you mean, and guessing is where agents go sideways.\n\nThe tighter your turns, the more control you keep. Large, fuzzy instructions produce large, fuzzy diffs that take longer to review than they would have taken to write. Small, specific instructions produce diffs you can read in a glance.\n\n## Files Versus Commands\n\nClaude Code works with two kinds of things, and keeping them straight helps you reason about what it is doing.\n\nFiles are state. They persist. When Claude edits a file, that change stays on disk until something else changes it. Editing files is how the agent makes durable progress: a new function, a fixed bug, an updated config. Every file edit is something you can see in a diff and commit to git.\n\nCommands are actions. They run, produce output, and finish. When Claude runs `npm test` or `git status` or `npm run build`, it is gathering information or triggering an effect, not writing code. Commands are how the agent verifies its own work. A change that compiles, a test that passes, a lint check that comes back clean. These are the evidence that the file edits were correct.\n\nThe healthiest sessions alternate between the two. Edit a file, run the relevant command, read the result, edit again. When an agent edits ten files without running anything, that is a warning sign. It is writing on faith instead of checking its work. A good instruction often bundles both: \"Refactor this module and run tsc to confirm nothing broke.\"\n\n## Read Before You Edit\n\nThe single most important behavior, for both you and the agent, is reading before editing. Claude Code is built around this. It reads a file into context before it changes it, because editing something it has not seen means editing a guess.\n\nThis matters for you too. When you ask for a change, the agent's first move is usually to read the files involved. That is not wasted effort. It is the agent building an accurate picture of what exists before it touches anything. A change made against a real understanding of the code is a change that fits. A change made against an assumption is the kind that compiles but breaks something three files away.\n\nIf you ever see Claude propose an edit that ignores how the surrounding code actually works, the fix is almost always to point it at the file it skipped. \"Read the existing handler in src/api/auth.ts first, then make the change.\" Reading is cheap. Wrong edits are expensive.\n\n## A Session in Practice\n\nHere is what a single turn looks like from the outside. The instruction is on the first line. Everything after is the agent working and reporting.\n\n```\n> Add a rate limit of 5 requests per minute to the login route, then run the tests.\n\n  Reading src/api/login/route.ts ...\n  Reading src/lib/rateLimit.ts ...\n  The project already has a rateLimit helper. I'll apply it to the login\n  handler rather than write a new one.\n\n  Editing src/api/login/route.ts\n    + import { rateLimit } from '@/lib/rateLimit'\n    + const limited = await rateLimit(request, { max: 5, windowMs: 60_000 })\n    + if (limited) return new Response('Too many requests', { status: 429 })\n\n  Running: npm test -- login\n    PASS  src/api/login/route.test.ts (4 tests)\n\n  Done. The login route now rejects a sixth request inside a 60s window\n  with a 429. All four login tests pass.\n```\n\nNotice the order. It read the relevant files first. It found existing infrastructure and chose to reuse it rather than reinvent it. It made a small, reviewable edit. It ran the tests to verify. Then it told you what changed and what it confirmed. Your job at this point is the review: is a 429 the right status, is five the right limit, do you want this on other auth routes too? That judgment is yours. The mechanical work was the agent's.\n\n## Driving an Agent, Not Writing Code\n\nThe mental shift that makes all of this click: stop thinking of yourself as the person typing the code. Start thinking of yourself as the person responsible for the outcome. The agent types. You decide what should be typed and whether what came back is good enough to keep.\n\nThis is a real change in where your attention goes. Less of it goes to syntax and boilerplate. More of it goes to the things an agent cannot do for you: deciding what to build, knowing what \"correct\" means for your system, and catching the subtle ways a plausible-looking change is actually wrong. The agent is fast and tireless. It is not the keeper of your intent or your taste. That part stays with you.\n\nThe engineers who get the most out of Claude Code are not the ones who write the cleverest prompts. They are the ones who give clear, bounded instructions, who insist the agent verify its work, and who read every diff before they accept it. The tool is powerful. The judgment is still yours, and that is the part worth getting good at."}
