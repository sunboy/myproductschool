{"hook_text": "Plan mode lets Claude Code read, search, and reason about your codebase without touching a single file, then propose a plan you approve before any edit lands. On multi-step work, this beats diving straight into code.", "body_mdx": "## Why Plan First\n\nThe fastest way to get a wrong change is to start editing immediately. Claude Code can write code the moment you ask, but on anything that spans more than one file or one decision, the first edit often locks in an assumption that later turns out to be wrong. Then the next edit compensates for the first, the third compensates for the second, and you end up reviewing a diff full of corrections to mistakes that never needed to happen.\n\nPlanning breaks that pattern. Before any file changes, Claude Code reads the relevant code, figures out where the work belongs, and writes down the approach. You read the plan, catch the wrong assumption while it is still a sentence, and only then does code get written. The cost of fixing a bad idea is one comment instead of a tangled diff.\n\nThis matters more as the task grows. A one-line rename does not need a plan. A change that touches an API route, a shared type, three components, and a migration absolutely does, because the order of those edits and the contract between them is the hard part, not the typing.\n\n## What Plan Mode Actually Does\n\nPlan mode is a read-only state. While it is active, Claude Code can use every tool that observes the codebase, reading files, searching for symbols, running git commands, inspecting types, but it cannot write or edit anything. The boundary is enforced, not a matter of good intentions.\n\nThe loop has three phases:\n\n1. **Explore.** Claude Code reads the files that matter, searches for related code, and builds a model of how the current system works.\n2. **Propose.** It writes a plan: what it understands, the approach it intends to take, the files it will touch, and how it will verify the result.\n3. **Approve.** You read the plan and either approve it, which exits plan mode and lets execution begin, or you push back and the plan gets revised before any edit happens.\n\nNothing in your working tree changes until you approve. That single property is what makes plan mode safe to run on unfamiliar code.\n\n```mermaid\nflowchart TD\n  A[Task arrives] --> B{Multi-step or unfamiliar?}\n  B -->|No| Z[Edit directly]\n  B -->|Yes| C[Enter plan mode read-only]\n  C --> D[Explore: read, search, inspect]\n  D --> E[Propose plan: context, approach, files, verification]\n  E --> F{Human approves?}\n  F -->|No, revise| D\n  F -->|Yes| G[Exit plan mode, execute edits]\n  G --> H[Run verification]\n  H --> I{Passes?}\n  I -->|No| D\n  I -->|Yes| J[Done]\n```\n\nThe revise arrow is the point of the whole thing. A rejected plan costs almost nothing. A rejected diff costs a re-review and often a revert.\n\n## What a Good Plan Contains\n\nA plan is not a vague promise to be careful. It is a structured document with four parts, and a plan missing any of them is weak.\n\n**Context.** What Claude Code now understands about the current state, in plain terms. Which files are involved, what they do today, what constraint shapes the change. This is where a wrong mental model surfaces. If the context paragraph describes the codebase incorrectly, you stop right there.\n\n**The approach.** The strategy, stated before the steps. Not \"edit these files\" but \"the type changes first because everything else depends on it, then the API route, then the components that consume it.\" The approach is the reasoning. The file list is just the consequence.\n\n**Files to touch.** A concrete list with one line each on what changes and why. This is the part you scan to catch scope problems. If a plan to fix a button touches a database migration, the list makes that obvious.\n\n**Verification.** How anyone will know the change worked. The exact command to run, the test that should pass, the page to load. A plan with no verification step is a plan that ends in hope.\n\nHere is the skeleton, the shape every good plan converges on:\n\n```markdown\n## Plan: Add per-team rate limiting to the upload endpoint\n\n### Context\nUploads currently go through `src/app/api/uploads/route.ts` with no\nlimit. Rate limiting helpers already exist in `src/lib/ratelimit.ts`\n(used by the auth route) but are keyed on user id, not team id.\nThe team id is available on `session.team` after `getSession()`.\n\n### Approach\nReuse the existing limiter rather than add a new dependency. Add a\nteam-keyed variant alongside the user-keyed one so both call sites\nstay independent. Wire it into the upload route as the first check\nafter auth, before any file is read, so a limited request costs\nnothing.\n\n### Files to touch\n- `src/lib/ratelimit.ts`: add `teamLimiter`, keyed on team id\n- `src/app/api/uploads/route.ts`: call `teamLimiter` after auth,\n  return 429 with a retry-after header when exceeded\n- `src/lib/ratelimit.test.ts`: add a case for the team key path\n\n### Verification\n- `npx tsc --noEmit` is clean\n- `npm test src/lib/ratelimit.test.ts` passes\n- Manual: POST eleven uploads in a minute from one team, the\n  eleventh returns 429\n```\n\nYou can read that in thirty seconds and know whether it is right. That is the entire value. The plan is small enough to review and specific enough to be wrong in a way you can catch.\n\n## Exploration Before the Plan\n\nA plan is only as good as the understanding behind it, and the understanding comes from exploration. On a small task Claude Code reads a few files directly. On a large or unfamiliar codebase, that direct reading can swallow the context window before the plan is even written, and a plan built on a half-read codebase inherits every gap.\n\nSubagents solve this. A subagent runs its own search in a separate context, then reports back a short summary instead of dumping every file it read into the main conversation. You can dispatch several at once: one to map how authentication flows through the app, one to find every place a given type is used, one to trace which tests cover the area you are about to change. Each returns a compact answer. The main session stays clean and spends its budget on the plan, not on raw file contents it will never look at again.\n\n```mermaid\nflowchart LR\n  M[Main session] --> S1[Subagent: map auth flow]\n  M --> S2[Subagent: find type usages]\n  M --> S3[Subagent: trace test coverage]\n  S1 --> R[Summaries return]\n  S2 --> R\n  S3 --> R\n  R --> P[Write the plan]\n```\n\nThe rule is simple. When research would cost more context than the answer is worth keeping, send a subagent to do the reading and bring back the conclusion. The plan gets the insight without the noise.\n\n## The Payoff\n\nPlanning pays off in three ways that compound.\n\nFirst, **fewer wasted edits.** A wrong assumption caught in the context paragraph never becomes a wrong file. The diff you eventually review is the diff that should exist, not a sediment of corrections. Less to read, less to revert, less to second-guess.\n\nSecond, **the plan is a shared contract.** Once you approve it, you and Claude Code agree on what the change is and what done looks like. There is no drift halfway through where the work quietly becomes something you did not ask for, because the boundaries were written down before any code moved. If execution starts to wander, the plan is the thing you both point back to.\n\nThird, **the plan is reviewable on its own.** A teammate, or a more capable orchestrator model, can read a plan and approve or reject it without reading a line of code. That is far cheaper than reviewing the implementation, and it catches design problems at the stage where they are sentences instead of merged commits.\n\nThe instinct to start typing is strong because typing feels like progress. On real work, the progress that counts is the wrong idea you killed before it cost anything. Plan mode is the place to do that killing, and approval is the moment the plan stops being a proposal and becomes the thing you build."}
