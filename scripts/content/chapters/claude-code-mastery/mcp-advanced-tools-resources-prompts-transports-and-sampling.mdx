The advanced layer is knowing which of the three primitives fits your data, which transport to run it over, and why your server keeps crashing the moment it writes a log line.", "body_mdx": "## Three Primitives, Not One\n\nThe intro chapter framed MCP as a way to give Claude Code extra tools. Tools are only one of three primitives the protocol defines. Each one solves a different problem, and using the wrong one is the most common design mistake when building a server.\n\n**Tools** are functions the model decides to call. They take arguments, run code, and return a result. They are model-controlled, which means Claude Code chooses when to invoke them based on the task. `execute_sql` is a tool because the model decides what query to run.\n\n**Resources** are data the server exposes for reading, addressed by URI. They are application-controlled, which means the host or the user decides what to pull in, not the model. A resource is closer to a file than a function. A BigQuery server might expose `bigquery://project/dataset/orders/schema` as a resource so the schema can be attached to context without the model spending a tool call to fetch it.\n\n**Prompts** are pre-written templates the server offers, usually surfaced as slash commands. They are user-controlled. A data server could ship a `/profile-table` prompt that expands into a full instruction for summarizing row counts, null rates, and cardinality, so the human picks it deliberately instead of retyping the same request.\n\nThe distinction that matters: tools are for actions the model takes, resources are for data the application injects, prompts are for workflows the user triggers. When the answer is \"the model should decide,\" build a tool. When it is \"this should always be in context,\" build a resource. When it is \"the human kicks this off,\" build a prompt.\n\n```mermaid\ngraph LR\n    subgraph Host[\"Claude Code (host + client)\"]\n        M[\"Model\"]\n        U[\"User / App\"]\n    end\n    subgraph Server[\"BigQuery MCP server\"]\n        T[\"Tools\\nlist_dataset_ids\\nget_table_info\\nexecute_sql\"]\n        R[\"Resources\\nbigquery://.../schema\"]\n        P[\"Prompts\\n/profile-table\"]\n    end\n    M -->|\"model-controlled call\"| T\n    U -->|\"app-controlled read\"| R\n    U -->|\"user-controlled trigger\"| P\n    style Host fill:#0d2e2e,color:#fff\n    style Server fill:#14b8a6,color:#fff\n```\n\n## Transports: stdio vs HTTP/SSE\n\nA server has to talk to the client over some channel. MCP defines two.\n\n**stdio** runs the server as a child process of Claude Code. Messages travel over stdin and stdout as newline-delimited JSON-RPC. This is the default for local servers because there is no network, no port, no auth handshake. Claude Code spawns the process, pipes to it, and kills it when the session ends. The BigQuery server you run on your own machine is almost always stdio.\n\n**HTTP with Server-Sent Events** runs the server as a network service. The client posts requests over HTTP and the server streams responses back over an SSE channel. This fits remote servers, servers shared across a team, and servers that need their own auth (OAuth, API tokens in headers). The Figma server in the intro chapter is HTTP because it lives at a hosted URL.\n\nThe tradeoff is reach versus simplicity. stdio is trivial to set up and impossible to share: the server only exists for the one Claude Code process that spawned it, and it inherits that machine's credentials and network access. HTTP is reachable by many clients and can sit behind real authentication, but now you own a deployment, a TLS certificate, and a token rotation story. Start with stdio. Move to HTTP when more than one person or machine needs the same server.\n\nConfiguration reflects the choice. A stdio server names a command to spawn; an HTTP server names a URL.\n\n```json\n{\n  \"mcpServers\": {\n    \"bigquery\": {\n      \"command\": \"npx\",\n      \"args\": [\"-y\", \"@google/mcp-server-bigquery\"],\n      \"env\": {\n        \"GOOGLE_CLOUD_PROJECT\": \"hackproduct-analytics\",\n        \"GOOGLE_APPLICATION_CREDENTIALS\": \"/abs/path/to/sa-key.json\"\n      }\n    },\n    \"team-metrics\": {\n      \"type\": \"http\",\n      \"url\": \"https://mcp.internal.example.com/metrics\",\n      \"headers\": {\n        \"Authorization\": \"Bearer ${TEAM_METRICS_TOKEN}\"\n      }\n    }\n  }\n}\n```\n\n## Sampling: The Server Asks the Model\n\nMost MCP traffic flows one direction. The model calls a tool, the server answers. Sampling reverses it. The server asks the client to run a model completion on its behalf.\n\nThis sounds backward until you see the use case. A BigQuery server gets a call to `execute_sql` and the query returns four thousand rows. Returning all of them floods the context window. Instead the server can use sampling to ask the client's model: \"summarize the distribution of these rows in three sentences.\" The summary goes back to the conversation, the raw rows stay on the server. The server gets language-model intelligence without shipping its own API key or model.\n\nThe value is that capability lives where it belongs. The server author does not pay for tokens, does not pick a model, and does not store a credential. The client controls cost and consent: Claude Code can show the sampling request, cap how often a server may ask, or deny it. A server that abuses sampling to run an expensive loop is visible and stoppable, which is the whole point of routing the request through the client rather than letting servers call models directly.\n\n## Notifications\n\nJSON-RPC supports messages that expect no reply. MCP uses these notifications for state that changes mid-session. The clearest case is `notifications/tools/list_changed`. If a server's available tools change while a session is live, say a BigQuery server gains access to a new dataset, it sends that notification and the client re-fetches the tool list. Without it, Claude Code would only learn about tools at startup and stay stale for the rest of the session. Progress updates on a long-running tool call ride the same mechanism. Treat notifications as the server's way of pushing news the client did not ask for.\n\n## Security and Permission Considerations\n\nAn MCP tool runs real code against real systems, so the permission model carries real weight. Three habits keep it safe.\n\nScope the credentials, not the prompt. The BigQuery service account in the config above should have read-only access to the analytics dataset and nothing else. If the only credential the server holds cannot drop a table, no amount of clever prompting makes the model drop one. The strongest boundary is the one the model cannot talk its way past.\n\nAllowlist reads, gate writes. Read tools like `list_dataset_ids`, `get_table_info`, and a read-only `execute_sql` are generally safe to permit broadly. Anything that mutates state stays explicit and per-call.\n\n```json\n{\n  \"permissions\": {\n    \"allow\": [\n      \"mcp__bigquery__list_dataset_ids\",\n      \"mcp__bigquery__get_table_info\",\n      \"mcp__bigquery__execute_sql\"\n    ],\n    \"deny\": [\n      \"mcp__team-metrics__delete_*\"\n    ]\n  }\n}\n```\n\nTreat tool results as untrusted input. A tool that fetches a web page or reads a user-authored database row can return text that tries to redirect the model. This is prompt injection arriving through a tool result instead of a chat message. The defense is the same as for any untrusted data: keep the credentials narrow so a hijacked instruction has nothing dangerous to reach for, and review tools that pull in arbitrary external content before allowlisting them.\n\n## Debugging an MCP Server\n\nTwo gotchas account for most of the time lost building stdio servers.\n\nThe first is the framing rule. On a stdio transport, stdout belongs to the protocol. Every byte written there must be a valid JSON-RPC message. The instant the server prints a stray log line, a stack trace, or a debug `print` to stdout, it corrupts the message stream and the client drops the connection with a parse error. The fix is absolute: never write anything to stdout except protocol messages.\n\nThe second follows from the first. All logging goes to stderr. The client ignores stderr for protocol purposes, so it is the only safe place to emit diagnostics. A server that logs to stderr can narrate everything it does without breaking the channel.\n\n```typescript\n// Correct: diagnostics go to stderr, never stdout\nconsole.error('[bigquery] execute_sql received, bytes:', sql.length)\n\n// Wrong on stdio: this corrupts the JSON-RPC stream and kills the session\nconsole.log('[bigquery] running query...')\n```\n\nWhen a stdio server connects but its tools never appear, or the session dies on the first call, suspect stdout pollution first. Run the server by hand, watch what it prints, and confirm that the only thing reaching stdout is framed JSON. Read the chatter on stderr to see where it stops. Once that channel is clean, most of the remaining bugs are ordinary schema mismatches between what the tool advertises and what it actually accepts.\n\nThe three primitives tell you what to build, the two transports tell you where to run it, sampling and notifications cover the conversations that flow the other direction, and the stderr rule keeps the whole thing alive long enough to use."}
